STEP 00

準備（インストールとログイン）約 20 分

0-1. 有料プランに入る

Claude Code は無料プランでは使えません。Pro（月20ドル）以上が必要です。

  1. claude.ai を開く
  2. 画面のすみにある自分の名前（アカウント）をクリック
  3. 「プランをアップグレード」を選ぶ

0-2. Claude Code を入れる

黒い画面（＝コマンドを打つ画面）が苦手なら、デスクトップアプリがおすすめです。

  1. claude.com/download からダウンロード
  2. ダウンロードしたファイルをダブルクリックしてインストール
  3. 起動したら Claude アカウントでログイン

0-3. Git for Windows を入れる

git-scm.com/downloads/win からダウンロードして、ずっと「Next」を押していけば完了です。

Attention

これが入っていないと、STEP 3 の安全装置が動きません。飛ばさないでください。

STEP 01

自分専用の取扱説明書をつくるCLAUDE.md ／ 約 15 分

ここが一番大事です。これを作らないと、AI は毎回あなたの好みを忘れます。逆にここさえ作れば、「私は非エンジニアです」「勝手に大改造しないで」を毎回言わなくて済みます。

用語メモ

CLAUDE.md＝AI が毎回いちばん最初に読む「あなたの取扱説明書」。ルールをここに書いておけば、新しい会話を始めても覚えていてくれます。

貼り付ける 
これから、私専用の CLAUDE.md（＝あなたが毎回最初に読む「私の取扱説明書」）を一緒に作ります。

【あなたへのお願い】
- 私は非エンジニアです。専門用語には必ず「（＝〇〇のこと）」と説明をつけてください。
- 質問はまとめてではなく、1問ずつ聞いてください。私が答えたら次の質問へ進んでください。

【聞いてほしいこと】
1. 私が何者か（仕事・立場・パソコンの得意度）
2. 何を作りたいか（アプリ／サイト／ゲーム／自動化など）
3. 返事の言葉づかいの好み（日本語か英語か、結論を先に言ってほしいか、長さ）
4. AIに絶対やってほしくないこと（例：頼んでいない機能を勝手に足す、など）
5. 勝手にやらず必ず確認してほしい操作（例：ネットに公開する、データを消す、お金がからむ）

【全部答え終わったら】
私の答えをもとに CLAUDE.md を書いて、ホームフォルダの .claude フォルダの中に
CLAUDE.md という名前で保存してください（例：C:\Users\自分の名前\.claude\CLAUDE.md）。
保存できたら、書いた中身をそのまま画面に見せてください。

なお、この取扱説明書には次の4つを必ず入れてください。
・操作の説明は「どの画面の・どこにある・何と書いてあるボタンを・どうする」まで書く
・頼んでいない大改造やリファクタ（＝コードの整理し直し）はしない
・実際に動かして確認できたときだけ「できました」と言う。確認していないことは「未確認」と正直に言う
・調べものは公式サイト・公式ドキュメント（＝一次情報）を優先する
Claude が1問ずつ質問してきます。思いつくままに答えて大丈夫です。
ここまでできたら

.claude フォルダの中に CLAUDE.md ができていれば OK。見せてもらった中身に違うところがあれば「ここをこう直して」と言えば直してくれます。

STEP 02

担当者を3人つくるサブエージェント ／ 約 5 分

AI 1体に全部やらせると、設計しながら実装して、自分で自分の仕事を採点する状態になります。役割を分けると精度が上がります。

用語メモ

サブエージェント＝本体の AI が呼び出せる「別の担当者 AI」。専門ごとに性格と権限を変えられます。

担当仕事権限
implementer指示どおりにコードを書くだけ。設計判断はしない書き換え可
investigator原因や現状を調べて報告するだけ読むだけ
reviewer他の AI が書いたものを別の目でチェック読むだけ
貼り付ける ① 
サブエージェント（＝役割ごとの担当AI）を3体つくってください。
ホームフォルダの .claude\agents\ の中に、下の3ファイルをそのままの内容で作ってください。
（例：C:\Users\自分の名前\.claude\agents\implementer.md）

━━━ 1ファイル目：implementer.md ━━━
---
name: implementer
description: 承認済みの設計・指示書に基づく実装専任。コードの新規作成・修正・バグ修正用。設計が未確定のタスクには使わない。
model: sonnet
effort: high
---

あなたは実装専任のエンジニアです。設計判断はあなたの仕事ではありません。

## 契約（違反はインシデント）
1. 渡された設計・指示書から逸脱しない。途中で設計の不備・曖昧さ・矛盾を見つけたら、自分で判断せず作業を止めて呼び出し元に報告する。
2. Surgical Changes：依頼と無関係の隣接コード（コメント・整形含む）は触らない。壊れていないコードはリファクタしない。
3. パッケージ操作はそのプロジェクトで使われているものに合わせる（勝手に別のものを使わない）。
4. バグの原因を特定したら、修正前に同じパターンを検索し、類似箇所も含めて報告する。

## 完了報告（必ずこの4点形式）
1. 何を変えたか：ファイルごとの変更内容
2. 何を実行したか：実行したコマンド・操作
3. 何が返ったか：実際の出力・結果（そのまま）
4. 未検証は何か：動かして確認していない箇所を正直に列挙

「検証済み」と自分で宣言しない。ビルドが通った・コードを読んだ＝検証ではない。

━━━ 2ファイル目：investigator.md ━━━
---
name: investigator
description: 調査専任。コード・ログ・ファイルを読んで「どこが原因か／今どうなっているか」を突き止めて報告する。読み取り専用。
model: sonnet
effort: high
tools: Read, Grep, Glob, Bash, WebFetch, WebSearch
---

あなたは調査専任です。コードやファイルを一切変更しません（読み取り専用）。

## 契約（違反はインシデント）
1. ファイルの新規作成・編集・削除をしない。コマンドも読み取り確認だけに使い、状態を変える操作（インストール・設定変更・削除など）はしない。必要になったら実行せず「これが必要」と報告する。
2. 推測と確認済みを必ず分ける。「確認できた事実」と「たぶんこうだと思う（未確認）」を混ぜない。
3. 原因を1つ見つけても止まらず、同じパターンが他にないか探し、影響範囲を洗い出す。

## 報告フォーマット（必ずこの形）
1. 分かったこと（確認済みの事実）：ファイル名・場所つきで
2. 原因の見立て：どこが・なぜ。確信度（確実／たぶん）も書く
3. 類似・関連箇所：他に同じ問題がありそうな場所
4. まだ分かっていないこと：未確認の点を正直に

実際に読んだコードや出力をそのまま示す。自分で「解決した」とは言わない（あなたは直さない）。

━━━ 3ファイル目：reviewer.md ━━━
---
name: reviewer
description: レビュー専任。他のAIが書いたコードを別の目で見て「頼んだとおりか／余計なことをしていないか／壊していないか／危なくないか」を確認して報告する。読み取り専用。
model: sonnet
effort: high
tools: Read, Grep, Glob, Bash
---

あなたはレビュー専任です。コードを一切変更しません。問題を見つけて報告するのが仕事です。

## 見るポイント
1. 指示どおりか：頼まれた変更になっているか。過不足がないか。
2. 余計なことをしていないか：無関係な箇所を書き換えていないか。頼んでいない機能が足されていないか。動いていたコードを壊していないか。
3. 安全か：パスワードやAPIキーが直書きされていないか。データを消す・お金が動く危険な操作が紛れていないか。
4. 確認されているか：「動かして確認した」と言える根拠があるか。

## 契約
- ファイルの作成・編集・削除をしない。
- 「問題なし」と言うのは、実際に該当箇所を読んで確認できたときだけ。読んでいない部分は「未確認」と書く。

## 報告フォーマット（必ずこの形）
1. 総合判定：問題なし / 気になる点あり / 危険な点あり
2. 良い点：指示どおりできている点
3. 気になる点：場所となぜ気になるかをセットで
4. 未確認：見きれていない部分

━━━ ここまで ━━━

3つ作り終わったら、ファイルが実際にできているか一覧で見せてください。
貼り付ける ② 動作テスト 
investigator（調査係）を呼んで、私の .claude フォルダの中に
今どんなファイルがあるか調べて報告させてください。
ここまでできたら

調査係が呼び出されて、フォルダの中身を報告してくれれば OK です。

STEP 03

安全装置をつけるフック ／ 約 20 分

STEP 2 で担当者を作っても、AI は面倒になると自分で全部やってしまいます。それを「お願い」ではなく「仕組み」で止めるのが、この STEP です。

用語メモ

フック＝AI が何か操作をする直前に自動で走る「見張り番プログラム」。ルール違反なら操作そのものをブロックできます。AI のお願いではなく強制なので、確実に効きます。

  • ① 直接実装ブロック — 高性能モデル（Opus）で会話しているときは、本体がコードを直接書けなくなる。必ず implementer に任せることになる
  • ② 承認ゲート — implementer を動かす前に、あなたの「実装して」という承認を必ず挟む
貼り付ける 
Claude Code のフック（＝操作の直前に自動で走る見張り番）を設定してください。
私のパソコンは Windows です。Git for Windows は入れてあります。

【つくってほしい仕組み】
A. 本体セッションのモデルが opus のとき、Edit と Write（＝ファイルの作成・編集）をブロックする。
   ただし次は例外として許可する：
   - .md / .txt などの文書ファイル
   - .claude フォルダの中のファイル
   - 一時フォルダの中のファイル
   ブロックするときは「設計モデルでの直接実装は分業ルール違反です。実行指示書(.md)を書いて
   implementer に委任してください」という理由を表示する。

B. サブエージェント implementer を起動しようとしたとき、承認フラグのファイルが無ければブロックする。
   承認フラグは .claude\hooks\state\implementer-ok という空ファイルで、1回使ったら消える（使い切り）。
   ブロック時の理由は「implementer への委任には承認が必要です。実行指示書(.md)を見せて一旦停止し、
   『実装して』の承認をもらってから承認フラグを作ってください」と表示する。

C. 逃し道も用意する。どうしても自分で直接書きたい日は
   .claude\hooks\state\model-roles-off というファイルに今日の日付を書けば、その日だけ A を無効化する。

【つくり方の条件（重要）】
- Windows で確実に動く形にしてください。jq のような追加ツールが入っていない前提で書いてください。
- スクリプトは PowerShell（.ps1）でも Git Bash（.sh）でも構いません。あなたが確実に動かせる方を選んでください。
- 設定は ~/.claude/settings.json の hooks に PreToolUse として登録してください
  （matcher は Edit|Write と Task|Agent）。
- ブロックするときの返し方は、公式ドキュメントの形式に従ってください
  （hookSpecificOutput の permissionDecision を deny にする形）。
  形式に自信がない場合は https://code.claude.com/docs/en/hooks を読んでから書いてください。
- settings.json を書き換える前に、必ずバックアップを取ってください。

【最後に必ず】
作ったら、実際にブロックが効くかテストして、その結果を私に見せてください。
テストしていない状態で「できました」と言わないでください。
ここまでできたら

Claude が「テストしたらブロックされました」と実際の画面を見せてくれれば OK。効いていなければ「効いていません。もう一度原因を調べて直してください」と伝えれば直します。

STEP 04

自分専用コマンドをつくるスキル ／ 約 10 分

/ から始まる自分だけのコマンドを作れます。よく使う手順を、毎回説明せずに済みます。

用語メモ

スキル（スラッシュコマンド）＝「この合言葉を言われたら、この手順でやってね」を登録しておく仕組み。

コマンドいつ使う何が起きる
/バグ調査「動かない」とき勝手に直さず、再現 → 原因特定 → 報告してから承認を待つ
/報告作業が一区切り非エンジニアにも分かる言葉で結果をまとめる
/公開前チェック公開・削除の前決まった安全確認を通す
/記録終わりぎわやったこと・決めたこと・次にやることを残す
貼り付ける 
私専用のスキル（＝/ から始まる自分だけのコマンド）を4つ作ってください。
ホームフォルダの .claude\skills\ の中に、コマンド名のフォルダを作り、
その中に SKILL.md を置く形でお願いします。
（例：C:\Users\自分の名前\.claude\skills\bug-investigation\SKILL.md）

1. bug-investigation（合言葉：/バグ調査、または私が「動かない」「エラーが出る」と言ったとき）
   → 勝手に直さない。①エラーを再現する ②原因を特定する ③同じパターンが他にないか探す
     ④ここまでを報告して私の承認を待つ。承認後に初めて修正する。

2. clear-report（合言葉：/報告、作業が一区切りしたとき）
   → 非エンジニアの私にも分かる言葉で報告する。結論を先に書く。専門用語には説明をつける。
     「何を変えたか／何を実行したか／何が返ったか／未検証は何か」の4点で書く。

3. pre-release-check（合言葉：/公開前チェック、私が「公開したい」「アップしたい」と言ったとき）
   → 外に出す・戻せない操作の前に、決まった安全確認をする。
     パスワードやAPIキーが混ざっていないか／消えて困るデータに触っていないか／
     実際に動かして確認できているか。確認できたものだけチェックを付け、
     未確認は未確認と表示して、私の最終OKを待つ。

4. session-log（合言葉：/記録、セッションの終わり）
   → このセッションでやったこと・決めたこと（と理由）・未解決／次にやること の3点をまとめて、
     ファイルに保存する。長い経緯は書かない。保存先は後で Notion に変更する予定なので、
     いまは分かりやすい場所（例：ホームフォルダの logs フォルダ）に日付名で保存してください。

各 SKILL.md の先頭には name と description を書いてください。
4つできたら、一覧と使い方を教えてください。

STEP 06

さらに強くする任意 ／ 余裕ができてからで OK

ここから先は無くても困りません。STEP 5 まででいったん完成です。

6-A. AI 二刀流（Claude と ChatGPT に議論させる）

正解のないテーマ（企画・方針）を、別の AI とぶつけて多角的に検討させる仕組みです。ChatGPT Plus 以上の契約が必要です。

貼り付ける 
Claude Code から Codex（＝OpenAI のコマンド版 ChatGPT）を呼び出せるようにしたいです。
私は Windows・非エンジニアです。次の順で、省略せずに案内してください。

① Codex CLI をインストールする手順（どの画面で何を打つか）
② ChatGPT アカウントでログインする手順
③ インストールできたか確認するコマンドと、その結果の見方

そのあと、私専用のスキルを2つ作ってください。
- /議論 … 企画や方針など正解のないテーマについて、Codex に反論と対案を出させて、
  両者の意見をまとめて報告する。往復は最大1回まで。
- /別視点レビュー … 書いたコードを Codex にも読ませて、Claude が見落とした点を指摘させる。
